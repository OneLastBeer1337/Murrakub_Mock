### P1 — Murakkab
*Chaudhry, G. I., Choukse, E., Qiu, H., Goiri, I., Fonseca, R., Belay, A., & Bianchini, R. (2026). Murakkab: Resource-Efficient Agentic Workflow Orchestration in Cloud Platforms. OSDI '26, pp. 567-587. arXiv:2508.18298.*

- **Role:** foundation (Technical base of the project)
- **Status:** in_references

**Summary:** A resource-efficient serving system for multi-tenant agentic workflows built on two principles: (1) a declarative workflow specification that decouples application logic from execution configuration, and (2) an adaptive, SLO-aware runtime that dynamically reconfigures workflows. Developers describe workflows as natural-language sub-tasks and data flow (no config details); an LLM-based orchestrator maps each sub-task to an executor (LLM / structured composition / tool) from a library, producing a request-agnostic Logical Workflow DAG. A profile-guided MILP optimizer then jointly selects workflow parameters, executor (model/tool), and hardware/parallelism per node, re-running periodically (every optimization epoch, e.g. 60 min in their eval) to adapt to fleet-wide load and multi-tenant multiplexing opportunities. Reduces GPU usage up to 2.8x, energy up to 3.7x, and cost up to 4.3x vs. static baselines while preserving SLOs.

**Problem:** Agentic workflows (multi-model, multi-tool, complex control logic) are becoming the dominant AI application paradigm, but today's frameworks (LangGraph, LangChain, AutoGen, CrewAI) expose them as opaque, imperatively-defined sequences of model/tool calls that tightly couple application logic with model and hardware choices. This fragmentation (across developers, frameworks, and cloud providers) prevents any single layer from reasoning about trade-offs across accuracy, latency, energy, and cost, causing resource waste and SLO violations. The configuration space (workflow-level knobs x agent-level knobs x hardware-level knobs) grows combinatorially with workflow depth and choices, and most developers lack the systems/ML expertise to navigate it manually -- they typically default to maximizing accuracy at the expense of efficiency.

**Method:** Murakkab manages the full workflow life-cycle across three phases: (1) DEVELOPMENT -- developers specify workflows declaratively as high-level sub-tasks in natural language (e.g. "Given a list of videos, identify scenes in each") plus the data-flow/dependency structure between them, with NO configuration details (no model choice, no resource allocation). A Workflow Orchestrator -- itself an LLM with tool-calling capability -- interprets this specification, parses tasks/sub-tasks, and maps each to an appropriate Executor from Murakkab's library. An Executor is one of three forms: (a) LLM (a specific LLM configuration -- fine-tuned, few-shot, or prompted), (b) Structured composition (an aggregation of models, e.g. self-reflection or LLM-Debate patterns), or (c) Tool (a utility module, e.g. an OpenCV frame extractor, web search, or any MCP-compliant third-party tool; traditional ML models like CNN classifiers also count as Tools). Each Executor in the library exposes a textual description, an interface spec, and a key-value list of configurable knobs (e.g. the frame-extraction tool exposes F=number-of-frames and cores; the LLM-Debate composition exposes D=debaters, R=rounds, model=which-LLM). The orchestrator's output is a Logical Workflow: a request-agnostic DAG where nodes are executors (chosen but not yet configured) and edges are data flow, with automatic type-checking between connected nodes (mismatches trigger LLM-based regeneration, or escalate to the developer if persistent). Separately, at RUNTIME, end-users may also invoke Murakkab with a raw natural-language query instead of naming a specific workflow -- the same LLM-based orchestrator then dynamically composes sub-tasks and maps them to executors or existing workflows on the fly ("Dynamic Workflow Requests"). (2) OPTIMIZATION AND DEPLOYMENT -- Murakkab builds two profiling layers ahead of time: Workflow Profiles (per representative workflow, quality/accuracy under varying workflow- and executor-level knob combinations, measured via benchmarks like VideoMME/HumanEval/MATH or curated/collected data, plus executor-level token load as a resource-usage proxy) and Model Profiles (per model, latency [TTFT/TPOT], energy, and cost across hardware and parallelism configurations). Profiling a given model/config is done once and reused across all workflows that use it. The Workflow Optimizer then combines both profile layers and solves a Mixed Integer Linear Program (MILP, solved with Gurobi, 300s time limit) that jointly selects (a) workflow parameters, (b) executor per node, and (c) hardware+parallelism, subject to per-request SLO constraints on accuracy/latency/cost (four tiers: best/good/fair/basic, corresponding to best/95th/80th/50th percentile values across the whole configuration space). The optimizer's procedure: first filter out configurations that violate the accuracy SLO, then use profiles to estimate latency/cost for the remaining configurations, then select the configuration meeting all SLOs (or return infeasibility). Beyond single-workflow optimization, the MILP jointly optimizes across ALL concurrently-registered workflows and SLO tiers system-wide, exploiting colocation/multiplexing of shared model instances across different workflows -- this is explicitly a MULTI-TENANT, fleet-wide optimization, not a per-workflow-instance decision. Re-optimization runs periodically on a fixed "optimization epoch" (their evaluation uses 60 minutes, chosen via a sensitivity analysis showing a 3-zone cost/utilization/responsiveness trade-off: 10-60min is buffer-dominated/high-transition-overhead, 60-180min is the balanced sweet spot, 180min+ is uncertainty-dominated/under-provisioned), using an EWMA-based load predictor (alpha=0.5) to project next-epoch demand from previous-epoch state. (3) EXECUTION -- incoming requests carry a workflow identifier (or raw NL query, see above), input data, and an SLO; Murakkab looks up the already-optimized Executable Workflow from its registry and dispatches it (request dispatch is deterministic given the selected workflow). A separate Auto-Scaler monitors per-model-instance load on a much shorter timescale (seconds-to-minutes) and rapidly scales instances to absorb short-term demand spikes/variance between optimization epochs, since per-request token generation (hence real resource demand) is highly input-dependent and cannot be predicted precisely in advance.

**Results:** Evaluated on three representative workflows (Video Q/A: scene detection -> frame extraction + speech-to-text -> object detection -> multimodal-LLM answering; Code Generation: LLM-Debate pattern with coder/tester agents; Math Q/A: self-reflect pattern) on Azure A100/H100 VMs using vLLM, using production-scale Azure LLM-serving traces (24h) to approximate agentic workload arrivals. Against a hand-crafted static baseline (fixed model+hardware, representative of LangGraph-style deployments), Murakkab (optimized, with multiplexing) reduces GPU count by up to 2.8x, energy by up to 3.7x, and cost by up to 4.3x while preserving accuracy and latency SLOs. On a combined video-QA + code-gen workload: static baseline used 2560 GPUs/80.4 MWh/$201.5k; Murakkab-optimized-alone used 1151 GPUs/27.1 MWh/$56.2k; Murakkab-optimized+multiplexed used 908 GPUs/21.6 MWh/$46.5k (a further ~21% GPU / ~20% energy / ~17% cost reduction purely from cross-workflow multiplexing on top of per-workflow optimization). On math-QA + code-gen: 2.7x fewer GPUs, 3.2x less energy, 3.5x lower cost vs. static. Demonstrated adaptivity to shifting hardware availability (e.g. trading A100s for H100s as H100 capacity becomes available, to minimize energy). A worked DAG-aware scheduling example shows Murakkab choosing a mixed CPU/GPU placement (OmDet on 1xA100, Whisper on CPU) that meets a 30s latency SLO with only 5 GPUs, vs. 6 GPUs for an all-GPU placement or an SLO violation for an all-CPU placement -- illustrating genuine cross-component trade-off reasoning enabled by end-to-end DAG visibility.

**Limitations:** The core optimizer is a MILP (solved via commercial solver Gurobi, 300s time limit per solve) -- this project's stated reason for departing from Murakkab's approach. Optimization/reconfiguration happens on a periodic, fleet-wide "epoch" cadence (60 min in their eval) across all concurrently registered multi-tenant workflows, explicitly optimizing for cross-workflow colocation/multiplexing -- this is a materially different cadence and scope than deciding once per individual workflow instance, which is the model this project has adopted instead (see caveats). Requires two natural-language-dependent, LLM-based components to function as designed: (a) a design-time orchestrator that interprets NL sub-task descriptions and constructs the Logical Workflow DAG via LLM tool-calling, and (b) an optional runtime path that dynamically composes a workflow from a raw NL end-user query. Both are explicitly out of scope for this project (see caveats). Workflow/model profiling requires either public benchmarks with ground truth (VideoMME, HumanEval, MATH) or curated/collected evaluation data per workflow -- profile quality is only as good as this evaluation data. Profiles are described as periodically refreshed from new data/feedback but the paper does not detail a continuous, per-execution online-updating mechanism comparable to this project's own drift-correction design; that remains this project's own novel contribution relative to Murakkab, not something Murakkab itself provides in detail.

**Key numbers:**
- Up to 2.8x lower GPU usage, 3.7x less energy, 4.3x lower cost vs. static baseline while maintaining SLOs
- Video Q/A + Code Gen combined workload: static 2560 GPUs/80.4 MWh/$201.5k -> Murakkab-Opt 1151 GPUs/27.1 MWh/$56.2k -> Murakkab-Opt+Multiplexed 908 GPUs/21.6 MWh/$46.5k
- Math Q/A + Code Gen combined workload: ~2.7x fewer GPUs, ~3.2x less energy, ~3.5x lower cost vs static baseline (4448 GPUs/169.87 MWh/$367.2k -> 1660 GPUs/52.66 MWh/$104.6k at best)
- Worked DAG-scheduling example: mixed CPU/GPU placement meets 30s latency SLO with 5 GPUs vs 6 GPUs (all-GPU) or an SLO violation (all-CPU)
- Optimization epoch sensitivity: 3 cost/utilization zones identified across 20min-6hr epoch lengths; 60min chosen as the balanced sweet spot in their evaluation
- MILP solved via Gurobi with a 300-second time limit per solve

### P6 — AgentOpt
*Hua, W., Karne, S., Xie, Q., Agrawal, A., Pagonas, N., Kaffes, K., & Peng, T. (2026). AgentOpt v0.1 Technical Report: Client-Side Optimization for LLM-Based Agent. arXiv:2604.06296v2.*

- **Role:** supporting (Client-side model-combination selection framework; strong conceptual and evaluation-methodology overlap with S1/S2, direct precedent for treating model assignment as a combinatorial search problem)
- **Status:** considered_partial_add

**Summary:** Introduces AGENTOPT, a framework-agnostic Python package for client-side optimization of multi-step agent pipelines, focused first on model-combination selection: given a pipeline with multiple roles and a candidate model pool per role, find the cost-effective model-to-role assignment via black-box combinatorial search (ten algorithms, notably Matrix UCB-E), rather than per-call routing. Central empirical finding: best combination does not equal the combination of best individual models — role interactions dominate, with 13-32x cost gaps between combinations at matched accuracy, and Matrix UCB-E recovering near-optimal accuracy at 62-76% less evaluation cost than brute force.

**Problem:** Existing agent-efficiency research is almost entirely server-side (caching, speculative execution, scheduling, load balancing), optimizing shared provider infrastructure. But developers building agent pipelines from heterogeneous models, tools, and APIs face a distinct client-side problem: how to allocate model choice, local tools, and API budget across pipeline stages/roles, subject to application-specific quality-cost-latency constraints that only the developer (not the provider) knows. Within client-side optimization, model selection is argued to be the dominant lever because it is upstream of every other optimization (caching/scheduling only matter after models are fixed), and because model quality is role-dependent, not a context-free property of the model in isolation — so the optimization unit must be the full model combination across all pipeline roles, evaluated end-to-end, not per-call routing of individual queries.

**Method:** Formalizes a pipeline with H roles and candidate model set(s) M_i per role; a 'combo' c = (m1,...,mH) is one full assignment. Executing combo c on the dataset induces trajectory tau(c) with measured PERF, LATENCY, COST; utility J(c) = U(PERF, LATENCY, COST), goal c* = argmax J(c) over the combinatorial space C = product of M_i (size can be exponential in number of roles). This is framed as a black-box / pure-exploration multi-armed-bandit problem: each combo is an arm, pulling it means evaluating on one datapoint. AGENTOPT implements ten search algorithms to explore this space sample-efficiently: Brute-force, Random search, Matrix UCB-E (treats the combo-by-datapoint grid as a matrix, UCB score = mean + sqrt(a/n), batches evaluation toward highest-UCB combo), Matrix UCB-E-LRF (adds a low-rank factorization ensemble to predict unobserved grid cells and target high-uncertainty cells), Arm Elimination (default method; rounds of evaluation with elimination of combos whose upper bound falls below current leader's lower bound), Epsilon-LUCB (targets epsilon-optimal best-arm ID via leader/challenger sampling), Threshold Successive Elimination (finds all combos above a quality threshold rather than the single best), Hill Climbing (local search over a role-by-role neighborhood, multiple random restarts), Bayesian Optimization (surrogate model + acquisition function, via BoTorch), and LM Proposal (uses an LLM to propose promising combos before empirical evaluation, without exhaustive search). Systems-wise, AGENTOPT is framework-agnostic: it intercepts LLM calls at the HTTP transport layer (patching httpx.Client.send / AsyncClient.send) and uses Python contextvars to attribute each call to the current datapoint and combo, requiring no changes to agent code. It includes HTTP-level response caching (keyed by request-payload hash, persisted to SQLite, preserving original latency even on cache hits) and a two-level semaphore for bounded parallel evaluation (across combos and across datapoints within a combo). Output is a ranked SelectionResults object with a Pareto frontier over accuracy/cost/latency, exportable to CSV/YAML.

**Results:** Evaluated on 9 models via AWS Bedrock (Claude Opus 4.6, Claude Haiku 4.5, Claude 3 Haiku, gpt-oss-120b, gpt-oss-20b, Kimi K2.5, Qwen3 Next 80B A3B, Qwen3 32B, Ministral 3 8B) across four benchmarks: HotpotQA (199 examples, 2-role planner-solver, 81 combos), GPQA Diamond (198 examples, single-role, 9 combos), MathQA (200 examples, 2-role answerer-critic, 81 combos), BFCL v3 Multi-Turn (200 examples, single-role, 9 combos). Central finding: at matched accuracy, cost gap between best and worst model combinations ranges 13-32x across benchmarks (e.g. on BFCL, Qwen3 Next 80B matches Claude Opus 4.6 accuracy at 32x lower cost). On HotpotQA, Claude Opus 4.6 (the strongest standalone model) is the worst planner across all 81 combinations because it tends to answer directly and bypass the solver's search tools; the best combo pairs the cheapest planner (Ministral 3 8B) with Opus as solver, reaching 74.27% accuracy vs only 31.71% when Opus is used for both roles. On algorithm comparison (50-seed averages): Matrix UCB-E is the strongest selector overall, recovering near-optimal accuracy while observing only ~20% of the evaluation grid, giving 62-76% cost savings vs brute force (e.g. HotpotQA: 73.54% mean acc at budget 0.2 vs 74.27% ground truth, using 3,234 evals vs 16,168 for brute force). Matrix UCB-E-LRF underperforms plain Matrix UCB-E despite its added complexity. Arm Elimination and Hill Climbing perform comparably on average (78.9% vs 79.1% mean accuracy across benchmarks) but Hill Climbing is sensitive to search-space topology (100% find rate on BFCL/GPQA, drops to 52% find rate on HotpotQA where the optimum is counterintuitive). LM Proposal (using an LLM's priors to propose combos) works only when raw capability predicts performance (GPQA) and fails badly where role interactions are non-obvious (HotpotQA, BFCL).

**Limitations:** Framed as a v0.1 technical report; model selection is presented as only the 'first functionality' of a broader intended client-side optimization package (future work explicitly includes adaptive routing, tool selection, scheduling, personalized utility-aware policies). Evaluation is limited to text/tool-use benchmarks with 2-role pipelines at most (no evidence yet for deeper/longer DAGs). Brute-force ground truth itself is nontrivial in cost even for 2-role, moderate-size pipelines (up to ~$124 for MathQA's 81-combo grid), which is the same tractability problem this project's own heuristic approach is designed to sidestep, but AGENTOPT addresses it via sample-efficient *search* over a fixed, whole-DAG-known set of combos rather than a *drift-adaptive, single-pass* heuristic scoring walk — a different design point from this project's DAG-walking allocator.

**Key numbers:**

- HotpotQA best combo (Ministral 3 8B planner + Claude Opus 4.6 solver): 74.27% accuracy, $51.90 brute-force cost over 81 combos
- HotpotQA worst-region: Opus-as-planner combos cluster near 31.7-32.0% accuracy across all 9 solver choices (ranks 71-79 of 81)
- MathQA best combo (Opus answerer + Haiku 4.5 critic): 98.84% accuracy, $123.87 brute-force cost over 81 combos

### P7 — MASTER (MARL for PPM)
*Bruinaars, P. (2025). A Multi-Agent Reinforcement Learning Approach to Prescriptive Process Monitoring. MSc Thesis, Utrecht University. Supervisors: X. Lu, S. Wang.*

- **Role:** supporting (Adjacent-domain precedent for decentralized, agent-per-resource task allocation under partial observability; strong methodological parallel for S1 (workflow/task execution modeling) and S3 (baseline-driven evaluation), different mechanism (learned RL policy vs. profile-guided heuristic scoring) for S2)
- **Status:** considered_partial_add

**Summary:** Presents MASTER, a Dec-POMDP-based multi-agent simulation environment for Business Process Optimization / Prescriptive Process Monitoring, where each resource (human or machine) executing tasks in a business process is modeled as an autonomous agent with partial observability, learning (via MAPPO or QMIX) when to volunteer for upcoming tasks from an event-log-driven task stream. Evaluated on three real/semi-synthetic datasets (CVS Pharmacy, Loan application, BPI12W) against three baselines (random, best-median, ground-truth), using throughput/waiting/processing time as metrics with non-parametric statistical testing (Kruskal-Wallis, Mann-Whitney U with Bonferroni, Cliff's delta). Results are mixed and dataset-dependent: QMIX generally outperforms MAPPO, MAPPO does best on CVS, QMIX on BPI12W, and both struggle on the loan-application dataset — no MARL approach uniformly beats the simple ground-truth/random baselines.

**Problem:** Existing RL approaches to Business Process Optimization (BPO) and Prescriptive Process Monitoring (PPM) assume a single centralized agent with full visibility over the process and its resources, which is unrealistic for real, distributed processes where many human/automated actors act with only local, partial information and must coordinate implicitly. No prior work had systematically applied Multi-Agent RL (MARL), modeling each resource as its own decision-making agent, to PPM/BPO using real event-log data.

**Method:** Models the business process environment as a Dec-POMDP: each resource (employee/machine) that can execute activities is an autonomous agent with a fixed set of capabilities (activities it can perform, with per-activity historical performance PDFs), a task queue, and a learned policy — no explicit 'type' or fixed schedule (simplified relative to the related AgentSimulator work). At each timestep, an upcoming task arrives from a stream (derived from the process's event log); agents each choose a binary action ('volunteer' or not) based on a partial observation (upcoming task identity, their own historical performance stats on that task type, current queue length, remaining duration of their current task, and capability flag for the upcoming task). If multiple agents volunteer, one is picked at random among capable volunteers; if none volunteer, one is picked at random among all capable agents. The task is added to the winning agent's FIFO queue. Reward is simply the negative throughput time of each task as it completes (f(d) = -d, d = completion_time - assigned_time), a deliberately simple, dataset-agnostic reward. Two MARL algorithms are trained on top of this environment: MAPPO (multi-agent PPO, on-policy, actor-critic with centralized-training-decentralized-execution/CTDE, clipped surrogate objective) and QMIX (value-based, off-policy, CTDE, per-agent Q-functions combined via a monotonic mixing network into a global Q-value, avoiding the exponential blow-up of the joint action space). The environment is implemented as a parallel PettingZoo environment (rebuilt from scratch rather than reusing the prior AgentSimulator/Mesa codebase, since Mesa isn't designed for MARL). Training is fully offline (80/20 train/test split on whole days of event-log data, non-overlapping start times), organized into training blocks (one full simulation pass per block, buffered and used to update policies over several epochs). Evaluation compares the resulting throughput/waiting/processing-time distributions against three baselines — random assignment, best-median-performer assignment, and ground-truth (as-logged) assignment — using Kolmogorov-Smirnov normality tests (which reliably fail, given heavy-tailed event-log data), Kruskal-Wallis H-tests for overall significance, and pairwise Mann-Whitney U-tests with Bonferroni correction plus Cliff's delta effect sizes.

**Results:** On the CVS Pharmacy dataset (6 resources, 15 activities, 10,000 traces): MAPPO gives a slight but statistically significant improvement in median throughput time over ground truth (driven by processing time, at a small cost in waiting time); QMIX performs statistically indistinguishable from random/ground-truth baselines but significantly beats the best-median baseline. On the Loan application dataset (19 resources, 12 activities, 1,000 traces): both MAPPO and QMIX perform worse than ground truth and random baselines on most metrics (though both beat the poor best-median baseline by a large margin) — the paper attributes this to long task durations combined with the one-task-per-agent-at-a-time assumption. On BPI12W (52 resources, 6 activities, 8,616 traces, real-world event log): QMIX is the best performer overall, beating all baselines and MAPPO on throughput and waiting time with small-to-large effect sizes, achieving a median throughput time over an hour faster than the next-best (ground-truth) baseline; MAPPO improves processing time but has worse waiting time than ground truth/random, netting a worse median throughput. Overall: QMIX generally outperforms MAPPO across datasets, but MAPPO wins on CVS specifically, so the thesis concludes there isn't enough evidence that one algorithm dominates the other; performance is highly dataset-dependent (interacting with number of resources, number of unique activities, and volume of training data).

**Limitations:** Explicitly exploratory/first-of-its-kind work: no formal hyperparameter tuning was performed (fixed hyperparameters chosen from preliminary experimentation, not grid search or Bayesian optimization); the simplified environment assumes each agent can work on only one task at a time and each case has only one active task/agent at a time, which the thesis itself flags as likely responsible for the poor loan-application results; the reward function (simple negative-throughput-time) is acknowledged as possibly numerically unstable and not necessarily optimal; conflict resolution when multiple/no agents volunteer is fully random, which the author suggests may be actively hurting performance and could be improved via inter-agent communication; results do not show a uniformly effective MARL approach — it sometimes underperforms even the trivial random-assignment baseline.

**Key numbers:**
- CVS: MAPPO median throughput 46.49 min vs ground-truth 47.85 min (small improvement); QMIX median throughput 47.85 min (~tied with ground truth)
- CVS Kruskal-Wallis throughput: H=4808.18, epsilon^2=0.075, p<0.001
- Loan application: MAPPO median throughput 3506.54 min vs ground-truth 2068.81 min (worse); best-median baseline median throughput 19437.93 min (far worse than all learned/other baselines)
- BPI12W: QMIX median throughput 119.56 min vs ground-truth 182.69 min (QMIX more than an hour faster at the mean/tail level); best-median baseline catastrophic at 536366.57 min median throughput
- Three datasets span 6/19/52 resources and 15/12/6 activity types (CVS/Loan/BPI12W), deliberately chosen to vary agent-count while keeping data volume workable for MARL training

### P9 — Update Opacity (Hatherley)
*Hatherley, J. (2025). A moving target in AI-assisted decision-making: dataset shift, model updating, and the problem of update opacity. Ethics and Information Technology, 27, 20.*

- **Role:** supporting (Philosophy-of-AI critique directly applicable to this project's drift-correction mechanism (C_DRIFT); the single most relevant paper found so far for the epistemic/safety risks of self-updating profiled estimates, a topic otherwise unexamined in the map)
- **Status:** considered_partial_add

**Summary:** Argues that regularly updating an ML system to counter dataset shift introduces a distinct sub-type of opacity -- 'update opacity' -- where users cannot explain why the current version of a model produces a different output than a previous version did on the same or equivalent input, even if each version's individual reasoning were otherwise inspectable. This causes 'intra-ML disagreement' (diachronic evolution over time at one site, and synchronic variation across sites/copies), which is argued to be more concerning than ordinary black-box inference opacity because it disrupts users' learned mental models of when to trust the system, causing measurable post-update performance drops in human-ML teams. Surveys candidate mitigations (post-hoc explanations, model reporting, performance validation, bi-factual explanations, dynamic model reporting, update-compatibility scoring) and finds each insufficient, tentatively favoring interpretable-by-design systems over black-box-plus-explanation approaches for high-stakes settings.

**Problem:** ML systems degrade over time due to dataset shift (technological changes in data collection, population/demographic drift, behavioral shifts in the population being modeled). The standard prescription is to regularly update/retrain the model to restore performance. Existing literature has examined the epistemic/ethical challenges of *how* to update (which data, which methodology), but had not examined the impact of updating on the human decision-maker using the system -- specifically, whether the *fact of having been updated* introduces its own distinct problem, independent of and additional to the ordinary 'black box problem' of not understanding a single model's reasoning.

**Method:** Introduces three updating frameworks from the literature (conventional: ad hoc updates, infrequent, minimal monitoring; dynamic: continuous monitoring but still discrete, periodic updates; continuous: continuous monitoring AND continuous updating, blurring research/practice boundaries). Distinguishes two pre-existing DNN opacity types (Sogaard 2023): training opacity (can't say how model parameters were induced from training data) and inference opacity (can't say why a given input produces a given output). Defines a new third type, update opacity, as a sub-type of inference opacity: users cannot say why the *current* version of a model produces output y from input x while a *previous* version produced a different output z from the same x. Distinguishes diachronic evolution (same system, same site, inconsistent outputs over time across an update) from synchronic variation (different copies of the same system at different sites, updated independently/asynchronously, giving inconsistent outputs on functionally identical inputs at the same time) -- both framed as instances of 'intra-ML disagreement.' Connects this to the pre-existing 'reconciliation problem' in ML epistemology (how should a user update confidence in their own judgment when it conflicts with an opaque model's output) and argues update opacity is a harder version of this problem because it is now not just human-vs-model disagreement but disagreement between two versions of the *same* model, with no clear reason to trust the newer one more. Evaluates 'computational reliabilism' (defer to whichever agent -- human or model -- is more demonstrably reliable) as a proposed general solution and argues it fails here because reliability is usually impossible to establish conclusively at the relevant level of granularity. Surveys and critiques six candidate mitigation strategies: post-hoc explanation models (saliency maps etc. -- static, can't explain change over time), model reporting / model cards (static, rarely updated, too coarse-grained), performance validation (better aggregate performance doesn't guarantee better human-ML team outcomes), bi-factual explanations (a proposed post-hoc method contrasting two *actual* past cases across model versions -- promising but undeveloped, and still only approximates rather than reveals true reasoning), dynamic model reporting / 'update cards' (infeasible if updates are frequent, and still too coarse), and update-compatibility scoring (maximizing the fraction of previously-correct outputs preserved across an update -- has a direct, formalized trade-off against how much overall performance improvement an update is allowed to deliver). Concludes by tentatively favoring interpretable-by-design AI over black-box-plus-post-hoc-explanation in high-stakes settings specifically because it is the only strategy considered that eliminates update opacity outright rather than just mitigating it.

**Results:** A conceptual/philosophical argument, not an empirical study -- no experiments of its own, but grounds its claims in cited empirical findings: e.g., model updates have been empirically shown to disrupt users' learned mental models and cause measurable, if temporary, drops in human-ML team performance immediately post-update (citing Bansal et al. 2019); the 'compatibility score' between two model versions (fraction of previously-correctly-handled cases still handled correctly after an update) is formalized following Bansal et al. 2019 as C(h2,h1) = fraction of examples h1 got right that h2 also gets right, and there is a documented empirical trade-off where forcing higher compatibility between versions measurably reduces the overall performance gains an update can deliver.

**Limitations:** Purely conceptual/normative -- offers no proposed technical solution to update opacity, only an inventory of why existing and near-future proposed strategies each fall short (each either doesn't address update opacity directly, is impractical at realistic update frequencies, still only approximates true reasoning post-hoc, or trades off against the very performance gains updating is meant to deliver). The paper explicitly ends by flagging this as an open research problem rather than a solved one. Domain focus is exclusively human-AI decision-making (mainly clinical/medical examples); does not consider fully-automated systems without a human-in-the-loop, or systems (like this project's own allocator) where updates happen far more frequently/continuously and at a much finer grain (per-task, per-config, via a lightweight EMA nudge) than the clinical model-retraining cadence the paper primarily has in mind.

### P10 — Palimpzest
*Liu, C., Russo, M., Cafarella, M., Cao, L., Chen, P. B., Chen, Z., Franklin, M., Kraska, T., Madden, S., & Vitagliano, G. (2024). A Declarative System for Optimizing AI Workloads. arXiv:2405.14696. (Also: Palimpzest: Optimizing AI-Powered Analytics with Declarative Query Processing, CIDR 2025.)*

- **Role:** foundation (Direct technical precedent for the structural-alternatives / workflow-reoptimization extension; the single most load-bearing paper for this project's own addition beyond Murakkab)
- **Status:** recommended_add_to_references

**Summary:** A declarative system for AI-powered analytics (Semantic Analytics Applications, SAPPs) that splits pipeline optimization into two jointly-searched layers: logical optimization (generates a set of provably-equivalent alternative pipeline structures via rules like filter/convert reordering, safe only where the user has declared operator dependencies) and physical optimization (generates candidate model/method/hardware implementations for each logical plan). A small number of cheap 'sentinel plans' are run on a data sample to estimate cost/runtime/quality for candidates before committing to full execution, letting the system pick the best overall (structure, implementation) combination against a user policy (min cost at fixed quality, etc.) without exhaustively evaluating everything. Achieves up to 90.3x speedup and 9.1x lower cost than a single-model baseline at comparable quality across three real workloads (legal discovery, real estate search, medical schema matching).

**Problem:** Building an AI-powered analytics pipeline over unstructured data requires making many interacting decisions (which model per sub-task, which prompting/inference method, which hardware, how to order operations) whose optimal values shift constantly as models, costs, and data change. Programmers today either hand-tune these decisions (brittle, constant rework as the landscape shifts) or use frameworks (LangChain, AutoGen) that focus on prompt management with no higher-level, optimizable task representation -- meaning structural choices (e.g. operation order) are baked in by hand and never systematically explored, leaving real efficiency gains on the table purely from pipeline shape, separate from whatever model-selection optimization is done.

**Method:** Programs are written as a chain of relational-style operators (Filter, Convert, GroupBy, etc.) over typed Datasets/Schemas -- a Convert operator transforms an object of one schema into another (e.g. TextFile -> Email), with its physical implementation (LLM call, synthesized code, etc.) deferred entirely to the optimizer, not specified by the user. Optimization proceeds in stages (Algorithm 1 in the paper): (1) generateLogicalCandidates -- apply logical optimizations (Filter Reordering: permute the order of selection filters wherever legal; Convert Reordering: move convert operations around the plan, e.g. after a filter that doesn't depend on it) to the initial logical plan, producing a SET of new plans that are logically/functionally equivalent to the original but may have very different cost/runtime, because reordering is only applied where the user has explicitly declared operator dependencies via a depends_on parameter -- the system does not infer or guess independence, it is told. (2) getPhysicalPlans with sentinel=True -- generate a small number of hard-coded 'sentinel' physical plans (e.g. one using GPT-3.5 for every operator, one using Mixtral, one using GPT-4) consistent with the logical candidates. (3) Run these sentinel plans on a small sample of input records (as little as 1-5% of the full dataset in their evaluation) to gather real execution statistics -- runtime, cost, and quality (assessed via a 'champion model' proxy for ground truth, per-operator). (4) Using these sampled statistics, generate the full, much larger set of physical plan candidates (hundreds to thousands) implementing all the logical candidates, and estimate their cost/runtime/quality without actually running them, using standard relational cost-estimation techniques plus the sampled operator-level statistics. (5) Eliminate clearly-dominated plans and reduce to the Pareto frontier over runtime/cost/quality. (6) Select the single best plan according to the user's declared policy (e.g. MinimizeCostAtFixedQuality(min_quality=0.8)) and execute it. Because Datasets are named and registered, and intermediate results are cached at the Dataset granularity, repeated or overlapping programs can reuse cached computation across runs.

**Results:** Evaluated on three real workloads: Legal Discovery (1000 Enron emails, identify fraud-related emails not quoting news sources), Real Estate Search (100 scraped listings, find modern/attractive homes within price and distance constraints, using both text and image data), and Medical Schema Matching (11 spreadsheets / 49 tables from cancer research papers, harmonize into a unified schema). Against naive single-model baselines (GPT-4, GPT-3.5, or Mixtral used for every operation), Palimpzest's selected plans achieved substantial simultaneous improvements: on Legal Discovery, a plan 4.7x faster and 9.1x cheaper than the GPT-4 baseline at 85.7% of its F1-score, and with parallelism enabled, 90.3x faster and 9.1x cheaper at 83.5% of baseline F1. On Real Estate Search, a plan 3.3x faster, 2.9x cheaper, AND with better F1-score (1.1x) than the GPT-4 baseline -- achieved specifically by reordering cheap text-based filters before the expensive vision-model-based filter, avoiding vision-model calls on candidates that fail the text filter first, plus input-token reduction (trimming listing text by 50%). On Medical Schema Matching, plans ~2.4x faster and ~4.6x cheaper with up to 1.2x better F1 than the GPT-4 baseline. Under three different explicit policies (max quality at cost/runtime budget; min cost at quality floor), the optimizer satisfied its target constraint in 7 of 9 tested policy-workload combinations, with compile/plan-selection time of only 2.6-13.1 seconds.

**Limitations:** Only two logical (structural) optimizations are actually implemented in the prototype -- filter reordering and convert reordering -- despite the paper explicitly envisioning more (splitting/coalescing LLM requests among them); the depth of structural search is therefore currently shallow relative to the space of possible pipeline rewrites. Reordering safety depends entirely on the user correctly declaring operator dependencies (depends_on) -- an incorrect or missing declaration could allow an unsafe reordering, since the system does not independently verify or infer these facts. Quality estimation relies on an unsupervised 'champion model' proxy (comparing against GPT-4's output as a stand-in for ground truth) rather than true labels in the general case, which is itself an approximation. The sampling/sentinel-plan approach has no rigorous, principled stopping criterion for how many samples are enough (acknowledged directly in the paper as 'admittedly naive'), and sentinel plan choices are made arbitrarily rather than optimized. The system currently caches at whole-Dataset granularity only, and does not yet handle continuous/streaming re-optimization as the underlying data or model landscape drifts after initial plan selection -- it optimizes once per program invocation, not on an ongoing, event-triggered basis over a long-lived, repeatedly-invoked workflow.

**Key numbers:**
- Legal Discovery: 4.7x faster, 9.1x cheaper than GPT-4 baseline at 85.7% of baseline F1 (single-threaded); 90.3x faster, 9.1x cheaper at 83.5% of baseline F1 (parallel, 32 workers)
- Real Estate Search: 3.3x faster, 2.9x cheaper, and 1.1x BETTER F1-score than GPT-4 baseline -- achieved via reordering (text filters before vision filters) plus 50% input token reduction
- Medical Schema Matching: ~2.4x faster, ~4.6x cheaper, up to 1.2x better F1 than GPT-4 baseline
- Policy satisfaction: 7 of 9 tested (policy x workload) combinations met their declared cost/runtime/quality constraint exactly
- Optimizer compilation/plan-selection time: 2.6s (Legal Discovery), 13.1s (Real Estate Search), 2.7s (Medical Schema Matching)
- Physical plan search space size in prototype: 234 (Legal Discovery), 10,140 (Real Estate Search), 1,950 (Medical Schema Matching) candidate physical plans generated per logical plan set
- Sentinel-plan sampling used as little as 5% of total input (1 of 11 inputs for Medical Schema Matching) to gather statistics used to estimate all candidate plans

Palimpzest's own related-work section explicitly and directly contrasts itself with Caesura (a system that DOES build the logical plan from natural language), stating plainly that Palimpzest 'makes no attempt at all to build the logical query plan from natural language' and expects a human programmer to supply the core processing logic -- this is a direct, citable precedent supporting this project's own decision to cut NLP entirely and require the incoming workflow to already be structured.

### P11 — DocETL
*Shankar, S., Chambers, T., Shah, T., Parameswaran, A. G., & Wu, E. (2024/2025). DocETL: Agentic Query Rewriting and Evaluation for Complex Document Processing. Proceedings of the VLDB Endowment, 18(9), 3035-3048. arXiv:2410.12189.*

- **Role:** supporting (Domain-relevant (document processing) precedent for pipeline restructuring, but its core mechanism (LLM-driven rewriting) conflicts with this project's NLP-cut decision -- useful for domain-specific decomposition patterns, not as a mechanism to adopt)
- **Status:** considered_partial_add

**Summary:** A system for optimizing complex, accuracy-sensitive document-processing pipelines (e.g. extracting every instance of a legal clause across long, heterogeneous documents) built on top of a declarative pipeline interface similar to Palimpzest's. Its key departure from Palimpzest and other declarative LLM-pipeline frameworks: rather than only reordering/selecting among a fixed set of pre-defined logical optimizations, DocETL uses an LLM agent to actively synthesize NEW rewritten operations (e.g. decomposing a single 'summarize this document' map step into a split-gather-map-reduce chain that processes overlapping chunks with neighboring context), verified by a second LLM acting as a checker of whether a rewrite is sufficiently optimized, iterating until it is. Demonstrates substantial accuracy improvements (not just cost/speed) on real document-analysis tasks by decomposing tasks and/or data that a single LLM call handles poorly.

**Problem:** Existing declarative LLM-pipeline frameworks (including Palimpzest, in its telling) mostly focus on reducing COST while executing a user-specified operation largely as-is, in a single LLM call -- they do not address the more fundamental problem that a single LLM call is often simply inaccurate for complex tasks over long or heterogeneous documents, even with a well-optimized prompt. Example given: reliably extracting every instance of a specific clause type (e.g. force majeure, indemnification) from a lengthy legal contract, or identifying every instance of officer misconduct across hundreds of pages of heterogeneous police records (reports, hearing transcripts, internal affairs files) -- tasks where the LLM's real bottleneck is DATA and TASK decomposition, not model selection or prompt tuning.

**Method:** DocETL provides a declarative interface (a YAML-based DSL) for users to define document-processing pipelines as chains of operators (broadly analogous to Palimpzest's Convert/Filter, but with document-specific operators like Map, Reduce). Its key mechanism is agent-based rewriting: rather than applying a small fixed library of provably-safe rules (as in Palimpzest), an LLM agent proposes NEW rewritten versions of an operation when the original is judged insufficient, and a second LLM acts as a verifier deciding whether an operation is 'sufficiently optimized' -- if not, rewriting continues iteratively. A canonical rewrite directive is 'split -> gather -> map -> reduce': decompose a long document into contiguous chunks, gather k neighboring chunks before/after each chunk as context, run the map operation (e.g. per-officer summarization) on each chunk with its neighbor-context included in the prompt, then reduce/aggregate results across chunks. Optimal chunk/batch sizes are shown empirically to be task-dependent (tested from 20% to 90% of the max context window), with some tasks favoring the smallest batches and others a middle size -- the paper explicitly flags this as requiring further research, not a solved parameter. When a new operation is synthesized mid-rewrite, it is immediately, recursively re-optimized ('opportunistic optimization') rather than only being checked once. The system also includes an evaluation framework for assessing rewrite quality on complex, hard-to-verify document tasks.

**Results:** Evaluated against declarative baselines including Palimpzest and Aryn, plus traditional NLP baselines (spaCy, NLTK), on tasks including legal contract analysis, video game review analysis, and analysis of declassified historical articles, using task-specific precision/recall metrics plus a hallucination-rate metric. Demonstrates significant accuracy improvements specifically from decomposition-based rewriting (not from cost/speed optimization) on tasks where a single LLM call systematically misses relevant information -- the paper's central empirical claim is that DECOMPOSITION, not just model/config selection, is often the binding constraint on quality for complex document tasks.

**Limitations:** The core rewriting mechanism is LLM-driven at both the generation and verification steps -- there is no rule-based, provably-safe-by-construction guarantee of the kind Palimpzest's filter/convert reordering offers; rewrite correctness rests on the proposing and verifying LLMs' judgment, not on declared formal properties. This is a direct architectural difference from what this project has adopted (Palimpzest's declared-dependency, rule-based rewriting), not a variation of the same mechanism. Optimal chunking/batching parameters are shown to be task-dependent with no general rule identified, requiring per-task experimentation. As with Palimpzest, there is no discussion of ongoing, event-triggered re-optimization of an already-deployed pipeline as data or models drift after initial optimization -- like Palimpzest, this is a once-per-pipeline-definition optimization process, not a continuously revisited one.

### P12 — DSPy
*Khattab, O., Singhvi, A., Maheshwari, P., Zhang, Z., Santhanam, K., Vardhamanan, S., Haq, S., Sharma, A., Joshi, T. T., Moazam, H., Miller, H., Zaharia, M., & Potts, C. (2024). DSPy: Compiling Declarative Language Model Calls into Self-Improving Pipelines. The Twelfth International Conference on Learning Representations (ICLR 2024). arXiv:2310.03714.*

- **Role:** foundation (Foundational precedent for declarative pipeline abstraction, modular DAG-based workflow composition, and separating logical pipeline structure from physical execution parameters (supports S1 and S2))
- **Status:** recommended_add_to_references

**Summary:** Introduces DSPy, a programming model and framework that separates the abstract structure of an information-processing pipeline (modules expressing text transformations and control flow) from the concrete parameters that execute it (model selection, prompts, and weights). Rather than brittle manual prompt engineering, DSPy pipelines are expressed declaratively as composable modules (Predict, ChainOfThought, ProgramOfThought, ReAct) in Python code. A compiler (teleprompter / optimizer) automatically optimizes the pipeline end-to-end against a user-defined metric (accuracy, format compliance, cost) by selecting demonstration examples, generating instructions, and updating weights. Evaluated across complex multi-hop QA, math reasoning, and system tasks; compiles pipelines that match or outperform expert-crafted prompts and larger models (e.g. compiling a 770M/7B parameter model to outperform uncompiled GPT-3.5) with orders of magnitude less manual effort.

**Problem:** Existing LLM applications are built through manual, trial-and-error prompt engineering that tightly couples the logical task definition with specific prompt templates and model quirks. When the underlying model, data distribution, or task requirements change, the entire pipeline must be manually re-tuned. Moreover, multi-step pipelines (chains of thought, multi-agent interactions, retrieval-augmented generation) suffer from cascading failure modes and combinatorial parameter spaces that human developers cannot effectively navigate by hand.

**Method:** DSPy introduces three core abstractions: (1) Signatures, which declaratively specify input/output behavior (e.g. 'question -> answer' or 'context, question -> rationale, answer') without prescribing prompting syntax; (2) Modules, which are composable, parameterized building blocks (Predict, ChainOfThought, ReAct, MultiChainComparison) that instantiate signatures and can be nested into arbitrary acyclic execution graphs (DAGs); and (3) Teleprompters / Optimizers (e.g. BootstrapFewShot, MIPRO, BootstrapFewShotWithRandomSearch), which take a declarative program, training/validation data, and an evaluation metric, and automatically optimize the pipeline end-to-end via multi-stage search, prompt synthesis, and candidate filtering. Optimization is programmatic, metric-driven, and reproducible.

**Results:** Evaluated across HotpotQA (multi-hop QA), GSM8K (math reasoning), and SQuAD, DSPy programs consistently outperform expert hand-written prompts and single-model baselines. In HotpotQA, compiled 2-step retrieval-augmented DSPy pipelines achieved 30-40% higher accuracy than standard zero-shot and few-shot baselines; compiling a smaller, cheaper open-source model (Llama-2-13B) enabled it to match or exceed the performance of uncompiled GPT-3.5-turbo while drastically reducing API serving cost. Compilation converged within tens to hundreds of metric-evaluated trials, demonstrating high sample efficiency relative to naive grid search.

**Limitations:** DSPy focuses on compiling prompting strategies, few-shot demonstrations, and model weights within a given software application process; it does not model hardware-level execution constraints (GPU instance allocation, throughput limits, GPU budget caps), which is this project's distinct systems contribution. Compilation requires an executable metric and a modest set of representative examples; where reliable automatic metrics are absent, optimization requires proxy evaluators or human annotation. DSPy assumes a centralized client runtime rather than multi-tenant cloud-scale hardware resource scheduling.

**Key numbers:**
- HotpotQA multi-hop QA: DSPy compiled pipeline achieves 30-40% higher accuracy vs standard zero-shot/few-shot baselines
- Compiled open-source model (Llama-2-13B) matches or exceeds performance of uncompiled GPT-3.5-turbo on multi-hop reasoning
- Demonstrates sample-efficient compilation converging within tens to hundreds of metric-evaluated pipeline passes
